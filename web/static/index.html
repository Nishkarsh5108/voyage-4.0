03 · Method

How Canon decides

Compare only what could be the same. Weigh the evidence. Spend the expensive judgement on the hard cases. Keep every difference a customer pays for.

3.1 · Hotels · Blocking

Don't compare everything

Checking every listing against every other would take comparisons. Canon compares a listing only with what is near it, or with names that look close anywhere in the city.

candidates per listing, keeping of the true pairsIndependent keys

3.4 · Hotels · Clustering

From pairs to places

Accepted pairs join into entities with union-find, strongest evidence first. One constraint holds throughout: two different Wikidata IDs never end up in one entity.

→Dubai lodging listings to hotels; described by two or more sourcesPipeline output

The rule is strict. Where Wikidata itself holds two items for one hotel, it refuses a true merge as well.

3.5 · Rooms · Room and rate

Split the rate from the room

A supplier's room string mixes the room with the rate plan. Canon parses them apart, then matches rooms on room attributes only. Room attributes are ink; rate attributes are orange.

vsrenamed rooms mapped to the right room, against the best fuzzy matcherSimulated supplier

Real room lists of hotels. The second supplier's strings are rule-based rewrites, so this measures robustness to renaming, not a live feed.

3.6 · Tours · Typed relations

Same, variant, includes, different

For tours, "duplicate or not" is the wrong question. Canon types each relation and keeps the difference as a chip the agent can see.

·of variants · of combos a plain deduplicator merges into the base productSimulated supplier

Real Klook Singapore products; the second supplier is simulated. The typed-relation rules were tuned on the same pairs, so their own accuracy is in-sample.

3.7 · Offers · Arbitration

Price the risk

Once listings are merged, offers sit side by side. Put a price on a failed booking and the cheapest offer stops being the best one.

    06 · Adoption

    Built to sit beside what exists

    Canon does not ask anyone to replace their hotel-mapping vendor. It takes that vendor's IDs as one more input and gets better wherever they disagree.

    How it fits
    1. Vendor IDs are an input. An existing mapping is one more key, used as a rule like a Wikidata ID.
    2. Disagreements go to review. When the vendor and the model disagree, the pair waits for a person rather than a guess.
    3. Thresholds live in configuration. Accept and reject bands are settings, not code, and can differ by market.
    4. Every merge is logged. Each entity records which pairs joined it and why, so any merge can be undone.
    What Round 2 adds
    1. Ranking on real search logs, once the Expedia benchmark's rules are accepted: LambdaMART against a position-bias-corrected baseline.
    2. Human labels for the prepared sheet of hotel pairs, so matching is reported against people, not only keys.
    3. The uncertain band: a cross-encoder trained on these pairs, then an LLM, then review.
    4. A second real tour supplier and a held-out set for typed relations.
    5. A review console and an API around this workbench.
