# Sightseeing: typed relations between products

Generated by `scripts/train/activities_benchmark.py`. Parser and relation function: `canon/activities.py` (deterministic, no model calls).

## Setup

- **Real**: 87 Klook Singapore products with coordinates, and a gazetteer of 1,506 Singapore attraction names taken from Wikidata, Wikivoyage and OpenStreetMap (the open POI layer; no Klook text went into it).
- The gazetteer finds at least one attraction in **57 of 87** product titles (65.5%); 4 titles name two or more (combos).
- **Synthetic second supplier**: 783 pairs, each a real product against a rewritten listing with a known relation.

### What a binary deduplicator does with the same pairs

A string matcher can only say *same* or *not same*. Share of each true relation it would merge (token-set similarity >= 85):

| True relation | Merged as duplicates |
|---|---:|
| SAME_AS | 98.3% |
| VARIANT_OF | 95.4% |
| INCLUDES | 100.0% |
| DIFFERENT | 0.0% |

It merges 95.4% of variants and 100.0% of combos into the base product, which loses the pickup, the meal or the second attraction. That is the difference the statement asks to keep.

## Reading the numbers

- The four-way score is on a **synthetic second supplier**. It shows the mechanism (attraction set + attribute diff) separates the four relations where string similarity cannot; it is not accuracy on two real suppliers.
- **The score is in-sample.** The relation rules were adjusted after reading the errors on this same set (first run: accuracy 85.1%, macro-F1 0.820, with combos under-detected). There is no held-out set yet, so expect a lower number on fresh data.
- Real cross-supplier evaluation needs a second real source for the same city. Viator's free Basic Access API is the planned one.
- Sibling options that come out as `SAME_AS` are the lexicon's blind spots (differences it has no word for); they are the queue for the model stage.
